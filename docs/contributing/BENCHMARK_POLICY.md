# 벤치마크 무결성 정책

높은 숫자보다 재현 가능하고 누수 없는 숫자를 우선합니다. 공개 개발셋을 보고 개선할 수는
있지만, 최종 주장은 구현을 고정한 뒤 별도 보류셋에서 확인해야 합니다.

## 필수 규칙

1. 질문, 정답 키워드, 기대 라우트를 런타임 코드나 프롬프트에 복사하지 않습니다.
2. 개발/검증/보류 분할과 생성 방법을 기록합니다. 같은 원문의 단순 바꿔쓰기는 같은 그룹에 둡니다.
3. 라우팅, 검색, 생성 정확도를 분리하고 전체 답변 정확도와 지연·오류도 함께 보고합니다.
   문항별 답변 채점은 `keywords` 기본 규칙 또는 `answerRule(anyOf/allOf/minMatches)`를 명시합니다.
4. 기준선과 후보는 같은 데이터, 모델, 설정, 반복 수로 실행합니다.
5. 평균만 보고하지 않고 문항별 원시 결과와 실패 분류를 보존합니다. 실행 하네스와 재채점 스크립트는
   같은 채점 함수를 공유해야 하며, 규칙 변경 시 재채점 결과 파일도 함께 남깁니다.
6. 100%는 해당 평가셋의 관측값일 뿐 일반적인 정확도 보장이 아님을 명시합니다.
7. Docker daemon이나 로컬 agent-app이 내려가 측정을 시작할 수 없으면 정확도 `0%`처럼
   집계하지 않고 `blocked` 상태 보고서로 남깁니다.

기존 평면 배열 결과를 다시 활용할 때도 `metadata`/`summary`/`rows` 구조로 정규화해
같은 실패 분류와 메타데이터를 남깁니다.

## 최소 통과 기준

- 공개 개발셋 라우팅 적중률 90% 이상
- 보류셋 라우팅 적중률 90% 이상
- 기존 키워드 포함 공식셋 라우팅 회귀 0건
- 파싱/호출 실패가 발생해도 안전한 기본 경로로 복구
- 결과 파일에 커밋, 모델, 설정, 반복 수 포함

목표를 충족하지 못한 후보도 삭제하지 말고 브랜치와 보고서에 실패 원인과 함께 남깁니다.
